# Contributing to Remit

Thanks for helping. Bug reports, conformance vectors, new connectors, SDK
improvements and spec clarifications are all welcome. For security issues, follow
[SECURITY.md](SECURITY.md) instead of opening an issue.

## Development setup

- Rust 1.98 or newer through [rustup](https://rustup.rs). `rust-toolchain.toml`
  selects the stable channel with the `wasm32-wasip2` and `wasm32-unknown-unknown`
  targets.
- Node.js ≥ 22.18 (the TypeScript tests run `.ts` sources directly).
- Python ≥ 3.10 and Go ≥ 1.23 for those SDKs.
- Optional: `z3` (policy proofs and `remit policy lint`), Lean 4 via
  [elan](https://github.com/leanprover/elan) (the formal model), `wasm-bindgen-cli`
  0.2.122 (the Wasm verifier for the TS SDK), `protoc`.

Build the engine components first; the Holder, the tests and the examples load them
from `engines/*/dist/`:

```bash
scripts/build-engine.sh all
```

```bash
cargo build -p bitsinfra-remit
```

## Checks

Push and pull-request CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml))
runs four parallel jobs, each with a five-minute timeout: the docs build and link
checks; Rust formatting, protocol tests and protocol lints; TypeScript SDK tests
against a verifier built from the checkout, plus reproducible vectors; and Python
and Go conformance tests. The Rust protocol job covers types, wire signatures, SQL
and receipts. These checks use unoptimized test builds and a pinned, checksummed
wasm-bindgen tool to keep cold builds short.

The full runtime and platform matrix, live integrations, full-workspace Clippy,
dependency advisories, MSRV, Cloudflare, benchmarks, proofs and fuzzing run through
the manually triggered [extended-validation workflow](.github/workflows/extended-validation.yml).
Run it from GitHub Actions or with `gh workflow run extended-validation.yml`.
Release packaging remains in its own workflow. Run the extended checks relevant
to your changes before releasing or merging runtime/security changes.

Local commands for the full checks are listed below.

| Area | Command |
|---|---|
| Rust tests | `cargo test --workspace --locked` |
| Lints | `cargo clippy --workspace --all-targets --locked -- -D warnings` |
| Optional connectors | `cargo test -p remit-read --features mysql,tantivy,lance,object-store` |
| Black-box conformance | `cargo build -p bitsinfra-remit && scripts/conformance.sh` |
| TypeScript SDK | `scripts/build-verifier.sh`, then in `sdk/ts`: `npm ci && npm run typecheck && npm test` |
| Python SDK | in `sdk/python`: `python3 tests/test_core.py`, and with `REMIT_BIN` set, `python3 tests/test_live.py` |
| Go SDK | in `sdk/go`: `go vet ./... && go test ./...` |
| Cloudflare backend | in `backends/cloudflare`: `npm ci && npm test` |
| Conformance vectors | `node scripts/gen-conformance.ts` must leave `spec/conformance/` unchanged |
| RemitBench | `node bench/remitbench/run.ts --spawn --quiet --require-parity` and `node bench/remitbench/adversarial.ts` |
| SMT lemmas | `scripts/prove.sh` |
| Lean model | `cd formal/lean && lake build`, then `REMIT_REQUIRE_LEAN=1 cargo test -p remit-types -p remit-policy --test lean` |
| Fuzzing | `cd fuzz && cargo +nightly fuzz run <target>` |

`live` tests that need Postgres or MySQL read `REMIT_TEST_PG_DSN` and
`REMIT_TEST_MYSQL_DSN` and are skipped when those are unset.

## Guidelines

- **Security-relevant changes need tests that fail without them**: a regression
  test, a property, a conformance vector or an adversarial case.
- **Keep the implementations in agreement.** Canonicalization, capacity, `remit_id`
  and type validation exist in Rust, TypeScript, Python and Go. A change to one
  needs the same change in the others and new vectors in `spec/conformance/`
  (generated by `scripts/gen-conformance.ts`).
- **Diagnostic codes are stable** and never reused; add new ones rather than
  changing the meaning of existing ones ([spec/VERSIONING.md](spec/VERSIONING.md)).
- **Spec first.** Behaviour visible to Senders or Holders belongs in `spec/` in the
  same pull request.
- **The kernel world lives in `spec/wit/kernel.wit`.** `crates/remit-kernel/wit/` holds
  a copy so the crate builds on its own; a test fails if the two differ.
- **New diagnostic codes** get an entry in [spec/diagnostics.md](spec/diagnostics.md);
  every diagnostic links to it.
- Changes to admission or instantiation hot paths are measured by the Callgrind
  gate; a regression over 5 % fails CI.

## Documentation

The documentation lives in `docs/` and uses the same Fumadocs/Next.js static-export
setup as Fusee and Gnomon. Use Node 24:

```bash
npm ci --prefix docs
npm run dev --prefix docs -- --port 4321
```

Build the static site, check its local links and assets, then preview it:

```bash
npm run build --prefix docs
npm run preview --prefix docs
```

The export is in `docs/out/`. It includes search, the full protocol specification,
downloadable JSON Schemas/WIT/protobuf, `llms.txt`, `llms-full.txt` and a Markdown
version of each page. The intended canonical host is `remit.bitsinfra.com`;
building this site does not publish it or configure that domain.

Write guides as Markdown or MDX under `docs/`. Put their navigation in
`docs/tooling/navigation.mjs`. SDK READMEs and specification files are imported
directly rather than copied into a second set of maintained pages. The
`<!-- example: examples/first-exchange.ts -->` directive prints a runnable example
from its source file in a guide. Keep example snippets and source paths complete.

The build checks every local page and asset link. When changing a quickstart, also
run its sender against the synthetic enterprise holder. Never describe a docs
build as verification of a live protocol exchange.
